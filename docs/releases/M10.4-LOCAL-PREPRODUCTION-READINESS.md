## 1. Executive Summary

The Jolinx Business OS ran the complete real-world business lifecycle end-to-end against a
production-like local environment (`LocalPreProduction`) backed by **PostgreSQL 17** (not SQLite).

close, reports, dashboard, tenant isolation, `X-Tenant-Id` non-trust, and the full auth lifecycle

bound against a PostgreSQL `timestamptz` column. Fixed and protected by a new regression test.

**All acceptance gates pass.** Final counts: Backend **598/598**, Flutter **261/261**,
`flutter analyze` **0 issues**, backend Release `-warnaserror` build **0 warnings**.

## 4. Configuration/Security Code Change (in-scope, genuine)

A genuine environment-safety defect was fixed so that demo credentials can never seed a
non-development environment:

- **`backend/src/Infrastructure/DatabaseSeeder.cs`**: `SeedAsync` signature changed to
  `SeedAsync(CancellationToken cancellationToken = default, bool createDemoTenant = true)`. The demo-tenant
  block (`admin@acme.local` / `Admin@12345`, `Acme Ltd`) is now guarded by
  `if (!createDemoTenant) { log ...; return; }`.
- **`backend/src/API/Program.cs`**: seeding gate extended — `Development`/`Testing` run
  `MigrateAsync()` + `SeedAsync()` (demo=true); the new `LocalPreProduction` branch runs
  `MigrateAsync()` + `SeedAsync(createDemoTenant: false)`.
  - Migrations are operator-applied (production-like); platform bootstrap (50 permissions + TRA tax
    catalog) is seeded; **demo tenant NEVER created outside dev/testing**.
- **Verified**: pre-prod DB has 50 permissions, 4 tax categories, **0 tenants, 0 users** after the
  seeder fix (no demo credentials present).

**Error classification**: Code defect (environment-safety). It does not expand scope: it only
prevents a dev-only data-seeding path from running in a production-like environment.

## 13. Fix: Date-only Report Query 500 + Regression

**What failed**: Calling `GET /api/v1/reports/sales-summary?from=2026-09-01&to=2026-09-02`
(date-only, no timezone) returned **HTTP 500**:
`Cannot write DateTime with Kind=Unspecified to PostgreSQL type 'timestamp with time zone', only UTC is supported.`

**Why it happened**: ASP.NET Core model-binding of date-only query values produces a
`DateTime` with `Kind=Unspecified`; the EF report queries bound these against the `timestamptz`
`SaleDate` column, which Npgsql rejects for non-UTC `DateTime` values. This affected
`sales-summary`, `tax-summary`, `top-products`, and (range-based) `sales-trend`.

**Why the fix is necessary & in scope**: This is a genuine 500 code defect on the accepted-V1
report endpoints, surfaced by M10.4's error-handling duty. Fixing it does not add features or
redesign; it restores correct, spec-compliant behavior.

**Fix** (`backend/src/Infrastructure/Persistence/Repositories/ReportRepository.cs`):
Added `NormalizeRangeUtc(from, to)` (`DateTime.SpecifyKind(..., DateTimeKind.Utc)`) and applied the
normalized UTC values in the EF predicates of `GetTaxSummaryAsync`, `GetSalesSummaryAsync`,
`GetTopProductsAsync`, and `GetSalesTrendAsync`. Date-only values are now bound as UTC and match the
`timestamptz` column.

**Verified after fix** (through the live HTTP endpoint):
- `sales-summary?from=2026-09-01&to=2026-09-02` → **200** (was 500)
- `tax-summary` (date-only) → **200**
- `top-products` (date-only + `limit=5`) → **200** (without `limit` returns 400 validation, correct)
- `sales-trend?days=7` → **200**

**Regression protection**: Added integration test
`Reports_DateOnlyRange_ShouldNotReturn500` in
`backend/tests/BusinessOS.Tests/Integration/BusinessLifecycleEndToEndTests.cs`. It drives the real
HTTP + EF path (register verified tenant, product, stock, a completed sale) then calls
`sales-summary`, `tax-summary`, and `top-products?limit=10` with **date-only** query values,
asserting HTTP 200 (not 500), and uses `limit` so it never mistakes missing-limit `.validation (400)`
for the datetime regression.

**Status: RESOLVED + REGRESSION-PROTECTED.**
